# 涉赌销售 · 账号体系挖掘与研判

## 零、强约定（最高优先级 · 不可违背）

> 以下为本技能的硬性契约，优先级高于本文件其余所有流程描述；与其它规则冲突时以本节为准。

### 0.1 本轮必答（最高优先级）
- **用户当前这一条消息，才是本轮唯一任务。** 必须以它为准作答。
- **禁止**用上一轮（或更早）已答复的内容顶替、敷衍或"复述式"回应本轮问题。
- 若历史上下文中**已有**本轮问题所需的依据/结论，且用户**未要求重查**，则**不得**重复调工具、重复解析、重复取证。
- 若本轮问题与上文**不同**，**不得**把上文答案作为本轮回复；应针对新问题重新判断、必要时补查。
- 判断不清用户问的是哪个实例/账号/时间点时，先澄清再动作，勿默认沿用上一问对象。

### 0.2 交付物一律用「账号 / 昵称」等人类可读标识，禁止裸露实例 GUID
- 报告中标识任何账号或实例，一律写成 **「账号 — 昵称」** 或 **「昵称（账号）」**，例如：
 - `{wx_main} — {业务昵称摘要}`
 - `{wx_cs} — {客服昵称摘要}`
 - `{qq_biz} — {业务 QQ 昵称}`
- **严禁**在正文、表格、图表、结论里直接暴露检材解析出的实例编号（形如 8 位十六进制 GUID 的短码）。
- GUID → 账号/昵称 的正确做法：读该 App 实例的**登录账号表**（见 §三），取 `ACCOUNT` + `REGIS_NICKNAME/ALIAS`。
 - 微信：`TBL_PR_WEIXIN_IM_ACCOUNT`（字段 ACCOUNT / REGIS_NICKNAME / RELID / MSISDN）
 - QQ：`TBL_PR_MOBILEQQ_IM_ACCOUNT`（字段 ACCOUNT / REGIS_NICKNAME / SIGN_NAME）
 - 诚信：`TBL_PR_CHENGXIN_*_ACCOUNT`；蝙蝠：`TBL_PR_BATCHAT_*_ACCOUNT`
- 登录表为空的实例 = **空白/残留库**，在报告中标注为「空白微信库 / 空白QQ库」，**不得**回退用 GUID 指代。
- 完整 GUID 仅允许出现在**附录/内部定位**（如证据出处、文件路径）中，且不作为读者理解主线。
- 表格若含"实例"列，应改为"账号"列；账号与昵称分列，便于阅读。

### 0.3 报告备注须带 Qiko 及版本号
- 每份交付物的页脚/备注**必须**注明生成工具与版本，例如：`本报告由 Qiko3.0 取证智能体 · 版本 v3.0 生成`。
- 同时注明数据来源（检材）与生成时间。

### 0.4 报告须含可视化（图表 / 关系图，HTML 自包含 + 自适应）
- 研判报告**不得是纯文字长文**，必须包含图形化呈现，至少覆盖以下几类：
 - **KPI 指标卡**：账号总数、单账号最大联系人量、明文口令组数、集中 IP 段数等关键数字大字突出。
 - **组织架构（硬门禁 · 缺则不合格）**：见 §0.5。不得用「见关系图」「略」或只写文字清单顶替。
 - **人物关系爆炸图（硬门禁 · 缺则不合格）**：见 §0.6。
 - **覆盖矩阵表**：按「应用 × 检材（如检材 A / 检材 B）」统计实例数与研判要点，用颜色标签区分类型。
 - **统计条形图**：账号数 / 联系人量 / 消息量等对比，用纯 CSS/SVG 内联条，避免外链图表库。
 - **类型色块标签**：区分「社交通讯 / 涉赌交易类 / 失联渠道」等。
- **格式与工程要求**：
 - 交付 **单文件 HTML**，**自包含**（CSS 与图形内联，无外链、无 CDN），离线双击即可查看。
 - 含 `viewport` + 自适应布局：页面 `width: min(100% - 24px, 1100px)`；KPI 用 `repeat(auto-fit, minmax(140px, 1fr))`；宽表外包可横向滚动容器。
 - 含 `@media print` 打印样式，A4 友好、图形不跨页断裂。
 - 配色统一、图例清晰；图表中的账号标注须遵守 §0.2（写账号/昵称，不出现 GUID）。
 - 图表数据须与正文一致，可溯源。
- **表格硬约束**（样式乱/列对不齐一律视为不合格）：
 - `table-layout: fixed` + `width: 100%`；单元格 `word-break: break-word; overflow-wrap: anywhere`。
 - 每一行 `<td>` 数必须等于表头列数；空单元格写 `—`。
 - **禁止**用 `colspan` 合并多台检材列；每台检材各自一列写账号。
 - **禁止**写死超宽固定像素把整页撑出横向滚动（允许单表容器内横向滚）。
- **SVG 硬约束**：
 - 必须有数值 `viewBox`；禁止 `height="auto"` / `width="auto"`。
 - SVG `width:100%; max-width:100%; height:auto`。
 - **禁止重叠**：节点框互不重叠、文字不溢出；连线不得穿过其它节点或文字，不得多条斜线叠在一起；连线标签不得压在线上或节点上。
 - 从左到右分列（操作人 → 本机账号 → 平台/口令/服务器），连线只走列间空白槽，用折线接到节点边缘。
- **模板复用**：若同时挂载 `huashu-design`，严格遵守其 `references/html-report-layout.md`；未挂载时仍须满足本节约束。

### 0.5 组织架构专章（最高优先级 · 硬门禁）
- HTML / Markdown 终稿**必须**有独立章节，标题固定为 **「组织架构」**（或同级 `h2`，禁止并入「账号清单」一笔带过）。
- 本章**必须**含一张内联 SVG 关系网，节点分层固定为：
  1. **操作人 / 枢纽人**（跨 App 同手机号并案锚点，如同一绑定号并案 `{wx_main}` + `{other_app_acct}`）
  2. **角色分包的本机 App 登录账号**（见下「角色标注」；微信 / QQ / 诚信 / 蝙蝠等）
  3. **涉赌平台账号**（备注台账挖出的品牌平台号）
  4. **口令**（有则挂边；无则该层可省略，但不得空章）
  5. **服务器 IP / 网段**
- **角色标注（硬要求 · 防「只列账号不分层」）**：每个本机账号节点第 2 行必须带角色之一：
  | 角色 | 判定线索（例） |
  |---|---|
  | 主销售 | 联系人量最大 / 案情点名主号 / 昵称含多品牌机器人 |
  | 客服发货 | 昵称含业务品牌/服务器等词；联系人量次级 |
  | 备用客服 | 同昵称系备用号 |
  | 核心业务 QQ | 案情/签名引流的业务 QQ |
  | 飞单/彩票 | 昵称含飞单/彩 |
  | 失联引流 | 蝙蝠 / 飞机 / 签名引流号 |
  | 工具售后 | 插件/售后类号 |
- 连线语义至少覆盖：`操作人—控制→本机账号`、`本机账号—台账→平台账号`、`平台账号—服→服务器`、`账号—口令→口令`（有证据才连）。
- **深挖硬清单（组织架构章正文必须交代，可表可卡，不得空话）**：
  1. **产品线与报价**：案情/聊天中的月费档位 → KPI 旁或组织架构下「产品报价卡」（写检材内实价，勿写死模板价）。
  2. **销售通道**：微信主号 / QQ 业务号 / 群发助手 / 群聊数（≥ 抽 3 个高相关群名）/ 防封引流（QQ·蝙蝠·飞机）——至少一段文字 + 通道清单表。
  3. **服务器租赁痕迹**：备注「服+IP」、聊天「服务器登录 / 搭建 / 租服」→ 归入服务器层；有口令则挂口令层。
  4. **品牌台账密度**：各品牌平台账号计数 → 条形图或小表；图上平台号仍 ≤8，密度进正文。
  5. **并案锚点**：同绑手机号跨 App 账号列表（写检材内真实绑定号，脱敏展示可用中间四位 `*`）必须写明。
- **节点不得「袋装聚合」**：禁止一个框写多个品牌名串在一起。图上只放本轮**最关键 ≤8 个**具体平台账号；其余写「另见平台清单表，共 N 个」。
- **节点文字**：每框最多 2 行；第 1 行账号（≤18 字），第 2 行角色或昵称缩略（≤16 字）；溢出截断 + `<title>` 放全文。禁止 emoji 进 SVG 文本。
- **连线完整性**：每个本机账号节点必须有自操作人出发的折线；有口令/服务器证据的平台号必须接到对应层——**禁止漏接**。
- **边旁短标签**：`控制` / `台账` / `口令` / `服`；放在列间空白，不得压线压框。
- **图例色 = 节点 fill**：逐字相同；操作人深蓝底须配同色图例。
- 若同时挂载 `huashu-design`：本章 SVG 按其布局合同；终稿由其写盘；标题写「组织架构」。
- **不合格判定**：无「组织架构」标题、无 SVG、无角色标注、无产品报价/销售通道交代、袋装聚合、漏连线、图例色不一致 → 返工。

### 0.6 人物关系爆炸图专章（硬门禁 · 上下线真人落地）
- 在「组织架构」之后，终稿**必须**另开一章，`h2` 标题固定为 **「人物关系」**（**禁止**写成「任务关系」）。
- 本章刻画销售链路里的**人物/关系向边**（介绍、派单、报账、失联），**不是**再画一张同构「组织架构」账号树。
- **核心目标**：把备注/聊天里的**上下线真人**解析成「账号 — 昵称」节点，并能在图与表里对应到具体人——**禁止**用「操作人 → 平台账号」冒充「介绍」。

#### 0.6.1 上下线落地（最高优先级 · 缺则不合格）
备注台账常见形态（必须识别并拆解；下表仅为**形态示意**，禁止把示意串当作真实账号写入报告）：
| 形态 | 示意模式 | 应挖出的人 / 边 |
|---|---|---|
| `{人名}{品牌}{平台号}` | `{人名片段}{品牌} {plat_xxx}` | 人前缀 → 查 CONTACT 得 `FRIEND_ACCOUNT`+昵称 → **下线/代理**；边=`介绍`或`派单`（看聊天） |
| `{品牌}{平台号}介绍{下级号}` | `{品牌} {plat_a} 介绍 {plat_b}` | 上家平台号 → 下级平台号；两端人都要尽量解析到联系人 |
| `主管 / 代理 / 飞单` 词 | `{品牌} {plat_xxx}（主管/代理）` | 角色写进落地表「角色」列 |
| 聊天「给你上线 / 加我上家 / 介绍个代理」 | 原文 | 上家/下家双方账号 — 昵称 + 出处消息时间 |

**落地步骤（必须执行，不可只扫品牌关键词）**：
1. 从 FRIEND_REMARK 用正则拆出：`人名片段`、`品牌`、`平台账号`、`服IP`、`介绍目标`。
2. 用人名片段 / 完整备注 **反查** 同库 CONTACT：`FRIEND_NICKNAME` / `FRIEND_REMARK` / `FRIEND_ACCOUNT` 模糊匹配，得到真实微信号/QQ 号。
3. 匹配失败时：落地表仍保留「备注人名片段」+ 关联平台号，角色标「待核验下线」，**不得丢弃**。
4. 输出强制表 **「上下线人员落地清单」**（人物关系章内，可在爆炸图前或边明细后）：
   | 角色 | 账号 — 昵称 | 关联平台账号 | 品牌 | 证据（备注原文或消息摘要） |
   |---|---|---|---|---|
   | 下线代理 / 上线介绍人 / 庄家 / 主管 / 待核验 | … | … | （检材内品牌） | … |
5. 图上「介绍」边的**至少一个端点**必须是落地清单里的真人（非操作人自己的本机号、非纯平台号冒充人）。

#### 0.6.2 边类型与伪介绍禁令
- **节点**（账号 — 昵称，禁止 GUID）：操作人、**已落地上下线**、主销售/客服本机号（作派单/报账通道）、平台号、失联渠道。
- **边类型**（无证据不连）：
  - `介绍 / 拉人`：备注「介绍 xxx」或聊天推荐上线；端点 = **上家真人 ↔ 下家真人/被介绍平台号**。  
    - **禁止**：`操作人/主号 → 平台账号` 仅因「备注台账里有该平台号」就标「介绍」（那是组织架构的 `台账` 边，人物关系应标 `派单` 或不画）。  
    - **禁止**：操作人自己的微信 ↔ QQ 互标「介绍」。
  - `派单 / 下发`：发号、发卡、后台地址、群发下载链接；起点 = 主销售/客服号，终点 = 平台号或服务器。
  - `报账 / 交款`：口令交接、余额、流水口述；起止与边明细一致。
  - `失联备用`：蝙蝠 / 飞机 / 备用 QQ；仅防封引流。
- **色码硬绑定**（节点 fill = 主边类型；四类边四色）：
  | 边类型 | fill |
  |---|---|
  | 介绍/拉人 | `#fdeeee` |
  | 派单/下发 | `#eaf1fb` |
  | 报账/交款 | `#eef7f1` |
  | 失联备用 | `#f3e8ff` |
  | 枢纽中心 | `#ffffff` + 描边 `#cfd8e3` |
- **图优化硬约束**：
  1. 无孤岛：外围节点必须有自中心或明确上家出发的 path。
  2. 等角扇区；中心半径 48–56；外围距中心 ≥120。
  3. 边标签短词，白底小标，不压线不压框。
  4. 图例外置一份；禁止 SVG 内双图例。
  5. 外图例四色与上表逐字相同。
  6. 图上 ≤8 外围节点；优先放**已落地上下线真人**，其次才是平台号/失联号；更多进表。
- **图 ↔ 表**：图边 ⊆「人物关系边明细」；落地清单可宽于图。
- **视觉交付**：主报告必须有内联 SVG；交互爆炸图技能默认不挂。
- **不合格判定**：标题「任务关系」、无上下线落地清单、介绍边全是「操作人→平台号」、伪介绍、孤岛、双图例、图边不在明细表 → 返工。

### 0.7 写盘前图与样式自检（对照实战翻车清单）
写 HTML 前必须逐条过；任一条否 = 返工：
1. 组织架构：每个可见本机号都有来自操作人的折线；口令/服务器有来自对应平台号的折线；本机号第 2 行有角色；正文有产品报价 + 销售通道；操作人图例色 = 节点 fill。
2. 人物关系：`h2` 是「人物关系」；有「上下线人员落地清单」；介绍边不是「操作人→平台号」冒充；无孤岛；单图例；四色分边；图边 ⊆ 明细表。
3. 无袋装聚合框；SVG 内无 emoji。
4. CSS：`.tagA` / `.tagB` / `.tagC` 与用到的 `.fill.*` 全部有定义。
5. 服务器资产表：无 `rowspan`/`colspan`。
6. KPI 与表计数口径不一致时必须 muted 说明。
7. **挂载协作**：若挂载 `huashu-design`，终稿 HTML 由其按布局合同落盘；禁止绕过另写合同外样式。
8. **挂载精简**：默认只需「涉赌销售账号 + huashu」；勿叠满四个重叠技能。

## 一、适用场景
- 网络赌博 / 六合彩 / 私彩 / 代理推广（业务黑话以案情为准）类案件。
- 检材为手机备份/镜像（iPhone/Android），含 **微信、QQ、诚信(ChengXin)、蝙蝠(BatChat)、WhatsApp、千牛(QianNiu)、QQPIM** 等。
- 诉求：把"账号"挖全 = **本机 App 登录账号 + 涉赌平台自身账号 + 关联联系账号 + 对应口令 + 服务器资产**，最终形成研判报告。
- 与脚本型技能 `phone-gambling-forensics`（SQL 模板自动生成、缓存加速）**互补**：本技能聚焦"账号体系"的识别与归类逻辑。

## 二、最关键认知（否则必漏）
"账号"分三层，缺任何一层都不算挖全：
1. **本机 App 登录账号** —— 在 App 的 Account 登录表里。
2. **涉赌平台账号** —— **不在登录表**，藏在联系人（尤其「诚信 ChengXin」）的**备注台账**里。这是本案最大发现点。
3. **关联联系账号** —— 署名/个性签名里暴露的蝙蝠号、飞机(TG)号、备用 QQ/手机号，是"防封号"失联渠道，本机往往**无登录态**。

## 三、数据位置

### 目录结构
```
<检材根>/data/MApps/<App名>{GUID}.mfs
```
- 每个 App 一个加密库；**同一 App 可能有多个实例**（不同登录态/残留），必须逐个读。
- 一律用 `sqlite_query_cli(db_path=...)` 直查（内置解密 key），**禁止** sqlite3 / bash 直接查 .mfs。
- 研判分析通道可用工具：`read` / `write` / `bash` / `edit` / `sqlite_query_cli`。

### 枚举全部实例
优先用宿主 prompt 已列出的主库绝对路径。若需补枚举：`bash` 逐层 `ls`（如 `ls "<检材>/data/MApps"`），或对已知路径 `read` 核对；再对每个 `*.mfs` 调 `sqlite_query_cli`。禁止递归 `find` / 全盘盲扫。

### 核心表（按用途）

| 登录账号 | 微信 | TBL_PR_WEIXIN_ACCOUNT | ACCOUNT / ALIAS |

## 四、执行流程（10 步）

1. **枚举实例**：按宿主列出的库路径，或用 `bash ls` 逐层找 `MApps/*.mfs`，统计每个 App 的实例数。
2. **取本机登录账号**：对每个 Account 表 `SELECT *`；空表也要记录（=空壳实例）。
3. **挖平台账号（核心）**：读诚信/微信/QQ 的 CONTACT 表，重点看 `FRIEND_REMARK`。备注命名规则 = **「（人名）＋ 平台品牌 ＋ 账号 ＋（服务器IP / 上级介绍人）」**，示意：`{品牌}{plat_xxx}服{ip}`、`{人名}{品牌} {plat_xxx}`、`{品牌}{plat_a}介绍{plat_b}`。按品牌归类（以案情/备注实见品牌为准）。
 - 行数多时**分页取数**：`LIMIT 27 OFFSET n`，避免 spill 截断。
 - **同步拆解上下线**：按 §0.6.1 拆人名片段 → 反查 CONTACT 落地「账号 — 昵称」→ 写入上下线清单；含「介绍」→ `介绍/拉人` 边；含「服+IP」→ 组织架构服务器边。
 - **禁止**只收集平台号字符串、丢掉备注前缀人名。
4. **提口令**：消息表关键词检索
 ```sql
 WHERE CONTENT LIKE '%密码%' OR CONTENT LIKE '%账号%'
 OR CONTENT LIKE '%网址%' OR CONTENT LIKE '%后台%'
 OR CONTENT LIKE '%上线%' OR CONTENT LIKE '%下家%' OR CONTENT LIKE '%代理%'
 OR CONTENT LIKE '%介绍%' OR CONTENT LIKE '%报账%' OR CONTENT LIKE '%交款%'
 ```
 另查：QQ 收藏、系统备忘录(Notepad)。字典表常为空，勿依赖。
 常见弱口令形态：短字母+数字、键盘序列、简单重复串等——**以检材原文为准写入报告，勿在技能文档中固化具体口令样例**。
 - 命中发号/派单/后台 → `派单/下发`；报账/交款 → `报账/交款`；推荐上家/加代理 → `介绍/拉人`（双方落地）。
5. **归集服务器资产**：正则提取全部 IP，按网段聚类；备注 `…服<IP>` 直接给出服务器；聊天「服务器登录/搭建/租服」补口令与用途。
6. **抽关联账号与销售通道**：签名/备注中的 蝙蝠号 / 飞机@ / QQ / 手机号 → `失联备用`；统计群聊（CONTACT 群类型或群消息表）与群发助手公告 → 写入组织架构「销售通道」。
7. **识别枢纽人与角色**：同绑手机号跨 App = 同一操作人；为本机号打 §0.5 角色标签（主销售/客服发货/业务 QQ/飞单/引流…）。
8. **组装组织架构图数据**：邻接表（`from | to | 边标签 | 出处`）行数 = SVG path 数；节点带角色；正文补产品报价 + 品牌密度 + 销售通道；禁止 GUID / 袋装聚合。
9. **组装人物关系**：先填「上下线人员落地清单」，再画爆炸图（优先真人节点）；校验无「操作人→平台号」伪介绍；边明细 ⊆ 证据。
10. **出报告前跑 §0.7 自检**。挂载 `huashu-design` 时由其写终稿 HTML；两章硬门禁不得删减。

## 六、易错点 & 经验
- **微信/QQ 多实例是正常的**，必须逐实例读，只看一个会漏号。
- **平台账号不在登录表，在联系人备注** —— 最关键一步，最易被忽略。
- **备注前缀人名 = 上下线线索**：`{人名}{品牌} {plat_xxx}` 里的人名片段必须反查 CONTACT 落地，不能只记平台号。
- **组织架构 ≠ 账号清单**：只列表无 SVG / 无角色 / 无报价通道 = 不合格（§0.5）。
- **人物关系 ≠ 再画一遍组织架构**：必须有真人上下线；`介绍` 边禁止「操作人→平台号」冒充。
- **实战翻车（已写入 §0.5–0.8）**：伪介绍；落地清单缺失；孤岛；双图例；漏连；袋装品牌框；绕过 huashu；叠满四个技能。
- 大数据量**分页取数**防 spill；细节读 spill 路径。
- **控制台 GBK**：避免 print emoji；**SVG 内禁止 emoji**。
- 检材只读；报告写 `output/` 或宿主指定路径。
- 语音(.amr)常口头报口令；口令缺失时提示转写。
- HTML 样式乱 / 表格错列 / 图贴边 = 不合格，按 §0.4–0.8 返工。
- **技能文档本身禁止写入真实检材数据**（真实账号、手机号、口令、公网 IP、人名备注原文等）；示例一律用 `{占位符}` / 形态描述。
